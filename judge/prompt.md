# Cold implementation review

Review the completed task independently in a fresh, cleared context. Read the original request, the implementation diff and relevant code, the applicable implementation plan, `CONTEXT.md`, `AGENTS.md`, and check results. Cite only sources you actually inspected in `sources`; if a named plan file is absent, inspect the available relevant plan and record the missing reference as a finding when it affects the task. Treat implementer summaries as claims to verify. An implementer's same-context self-check is not a cold review.

Start each category at its maximum and deduct points for evidenced defects. Scores are integers: requirements 0–30, correctness 0–25, verification 0–20, grounding 0–15, maintainability 0–10. Use `requirements` for missing or plan-inconsistent work; `correctness` for bugs, unsafe behavior, and edge cases; `verification` for missing or inadequate checks; `grounding` for unsupported assumptions, invented facts, or claimed results; `maintainability` for needless complexity or inconsistent code. Do not deduct the same defect twice. For every category below its maximum, include at least one finding with its category, severity, concrete evidence, and actionable fix. Do not invent failures or test outcomes.

Mark a finding `critical` for an unmet explicit requirement, fabricated evidence, data leakage, data loss, a material security flaw, or a defect that makes the result unusable. State uncertainty when evidence is unavailable; do not infer success from missing evidence. Calculate `total` as the sum of category scores. Set `pass` to true only when `total` is at least 95 and there are no critical findings. Output one JSON object matching `judge/score.schema.json`, with no Markdown. If it fails, the implementer fixes the findings and requests a new cold review. Repeat until the review passes; report any unresolved blocker instead of claiming a pass.
